一个系统在原团队的机器上稳定运行，并不代表它已经能够交给另一组人。

我处理过一套 AI 视频工作流自动化系统的源码交付。它不是单体小工具：用户端负责上传素材、编排任务和查看结果；Python 后端负责数据库、第三方生成接口、对象存储与 WebSocket 推送；另有一套管理后台处理用户、任务和运营数据。系统还依赖 PostgreSQL、Redis 与 FFmpeg。

功能开发完成时，我原以为剩下的是“整理一下文档”。真正开始交付才发现，源码包里藏着另一套产品：它由账号、环境变量、数据库命名、云资源、启动顺序和团队内部约定共同组成。

如果这些东西没有被重新划界，交出去的只是一个离开原环境就会失忆的工程目录。

这篇文章不讨论客户与具体业务，也不会展示任何真实账号、密钥和数据。只复盘源码从“内部能跑”变成“外部能接手”时，必须完成的几类工作。

## 第一步不是压缩代码，而是画出运行边界

交付前，我先把系统按实际运行关系重新列了一遍：

```text
用户端 Vue 应用
  -> FastAPI 后端
     -> PostgreSQL
     -> Redis
     -> FFmpeg
     -> 第三方视频生成 API
     -> 对象存储
  -> WebSocket 状态更新

管理后台
  -> 同一后端与数据库
```

这张图的意义不在于介绍技术栈，而在于暴露依赖所有权。

例如，第三方 API 与对象存储属于谁？数据库里是否混有原环境数据？Redis 是缓存还是任务状态的一部分？管理后台是否依赖只有原团队才知道的数据库视图？前端显示的“开发环境”和“生产环境”，究竟来自构建参数，还是来自后端的一段隐式判断？

只有先回答这些问题，才知道哪些内容可以随源码交付，哪些必须替换为配置，哪些需要生成空白本地实现，哪些应该明确列为外部前置条件。

## 删除凭证只是起点

最直观的风险是源码和历史配置里的凭证。

我把硬编码的数据库连接、对象存储配置和第三方服务信息从交付版本中移除，运行时统一从 `.env` 读取。交付包只保留字段说明与示例值，不保留能够连接任何真实资产的内容。

但“全文搜索没有密码”还不够。凭证可能出现在：

- 默认配置与备用连接字符串；
- 启动脚本和临时迁移脚本；
- 前端构建变量；
- 示例请求、测试数据和日志；
- 文档截图、数据库导出与异常堆栈；
- 代码里看似无害的云资源 ID、桶名或内网地址。

因此，脱敏检查需要按“身份与资产线索”搜索，而不只是搜索 `password`。最终目标也不是让文本看起来干净，而是确保接收方拿到源码后，无法意外访问原团队的任何生产资源。

## 最难清理的是隐式环境约定

这套系统历史上同时服务开发与生产环境，部分路由选择依赖数据库名称和特定视图是否存在。

在原环境里，这种约定一直有效：数据库名带某个后缀，就被识别为开发环境；存在一组跨库视图，管理后台就允许切换数据范围。开发团队知道这套规则，因此很少把它当成问题。

到了本地交付环境，隐式约定同时失效：

- 新数据库名称不符合旧判断，界面把本地空库标成了“生产”；
- 本地没有原云数据库的跨库视图，管理后台的一部分按钮被禁用；
- 前端状态、后端环境判断和真实数据来源出现了三套含义。

这类问题最危险的地方，是系统未必报错。它可以启动，也可以显示页面，但接手者无法判断某个灰色按钮是产品限制、部署失败，还是历史架构遗留。

处理时我没有把整套多环境架构重新推翻。交付目标是提供一个隔离、可运行的本地版本，于是我做了三件更具体的事：

1. 所有数据库访问统一降级到接收方自己的本地数据库；
2. 清除原生产连接与跨库数据来源，确保查询不可能越过交付边界；
3. 把仍然存在的界面文案和禁用逻辑写进交付说明，解释它们的来源、影响和后续改造位置。

这是一个有意识的兼容方案，而不是假装历史约束不存在。交付版本首先保证数据隔离和可运行；界面语义的彻底重构则被明确留给后续版本。

## 把“我知道怎么启动”改成机器可执行的顺序

内部开发时，启动步骤常常分散在人的记忆、终端历史和聊天记录里。源码交付要求把它们变成另一位开发者可以独立执行的流程。

最终文档按依赖顺序拆开：

1. 准备 Python、Node.js、PostgreSQL、Redis 与 FFmpeg；
2. 创建本地数据库并配置环境变量；
3. 安装并启动 FastAPI 后端；
4. 启动用户端前端；
5. 启动管理后台；
6. 检查 API 文档、WebSocket、文件处理和前端访问；
7. 说明生产部署时的 Nginx、进程守护和数据库替换位置。

每一段都需要回答四个问题：在哪个目录运行、执行什么命令、成功时看到什么、失败时先检查什么。

“运行 `npm install`”不是完整说明。如果项目要求特定 Node 版本、后端必须先启动、数据库 schema 需要初始化，或者 FFmpeg 必须进入全局 PATH，这些都属于交付接口的一部分。

## 配置模板应该说明责任，而不只是列出键名

一个常见做法是提供 `.env.example`，把值全部留空。它比泄露真实配置好，但仍然可能让接手者面对几十个不知用途的变量。

更有用的配置说明需要标出：

- 本地运行必填还是可选；
- 由交付方自己创建，还是由第三方平台提供；
- 缺失时功能降级，还是整个服务无法启动；
- 开发与生产环境是否使用不同值；
- URL、端口和路径的格式约束；
- 哪些值属于秘密，不能进入版本控制。

当这些责任被写清楚，配置文件才从“原作者的备忘录”变成真正的部署契约。

## 验收标准不能只写“页面打开了”

一个多服务系统打开首页，只证明静态资源或前端开发服务器正在工作。交付验收至少需要覆盖：

- 全新数据库能否完成初始化；
- 后端是否连接本地 PostgreSQL 和 Redis；
- 用户端能否调用 API 并收到实时状态；
- 管理后台能否读取本地数据；
- 文件上传、FFmpeg 处理与对象存储配置是否按预期工作；
- 第三方 API 未配置时，错误是否清楚且不会污染其他任务；
- 源码、日志与构建产物中是否仍含原环境身份信息；
- 重启后任务与数据状态是否符合文档描述。

如果交付环境暂时无法验证某个第三方能力，也要把它写成明确的未验收项，而不是用“理论上可以”替代。

## 我现在使用的源码交付检查表

后来我把这次工作归纳成一份更短的检查表。

### 资产与安全

- [ ] 源码、脚本、文档、日志和数据库样例不含真实凭证；
- [ ] 交付版本无法连接原团队的生产数据库、存储和第三方账号；
- [ ] `.env.example` 只保留字段与安全示例；
- [ ] Git 忽略规则覆盖本地配置、上传文件和运行日志。

### 环境与数据

- [ ] 数据库可以从空白状态初始化；
- [ ] 开发、交付和生产环境的判断规则有文档；
- [ ] 隐式命名、视图、端口和目录约定已经显式说明；
- [ ] 缓存、队列、临时文件和持久数据的所有权清楚。

### 启动与维护

- [ ] 每个服务有独立启动命令与成功信号；
- [ ] 启动顺序、依赖版本和系统工具有说明；
- [ ] 常见失败有可定位的检查路径；
- [ ] 生产部署与本地开发的差异被单独标出。

### 验收与边界

- [ ] 核心业务链路在干净环境完成一次端到端验证；
- [ ] 尚未验证的外部能力被明确列出；
- [ ] 历史兼容逻辑没有伪装成新的产品设计；
- [ ] 接手者能够在没有原作者现场操作的情况下复现。

## 源码交付也是产品工程

这次经历改变了我对“项目完成”的判断。

功能开发完成，只代表原团队已经获得一套可工作的实现。能够交付，则意味着系统的身份、依赖、状态和失败方式都可以被另一组人理解并接管。

它要求的不是再堆一批功能，而是减少隐含知识：把人的记忆变成文档，把生产资产变成可替换配置，把历史偶然形成的规则变成明确边界。

这部分工作不容易出现在产品截图里，却直接决定源码离开作者后还能不能活下去。
